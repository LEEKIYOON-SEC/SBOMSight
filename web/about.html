데이터 모델 3층 분리

내부 자산 정보와 공개 advisory 정보가 같은 객체에 섞이면 유출은 시간 문제다. 그래서 계층을 타입으로 갈라 두었다. 외부 전송 객체를 만드는 함수는 로컬 계층을 인자로 받지 않으므로, 실수로 넣는 것 자체가 불가능하다.

InstalledPackage AI 미전달

name · version(실제 설치 버전) · purl · cpes · locations(파일 경로) · sbom_ref

Detection AI 미전달

matcher · match_type · namespace · search_criteria

FixAnalysis AI 미전달

is_vulnerable · update_available · fix_state · version_gap · comparator

RuleVerdict AI 미전달

priority · fired_rules · flags · policy_version · policy_sha256

AdvisoryPackage 전달 가능

advisory_package · advisory_ecosystem · affected_version_range · fixed_version · os_family

VulnIntel 전달 가능

cve · cvss · cwe · epss · kev · exploit_available · exploit_maturity · exploit_sources
주의해서 볼 지점 — advisory_package는 공개 advisory가 지목한 식별자이지 우리가 설치한 패키지가 아니다. 문자열이 같아 보여도 다른 개념이다. 같은 이유로 affected_version_range·fixed_version은 advisory가 공표한 값이며, 자산에 깔린 실제 설치 버전은 전달되지 않는다.

AI에 전달되는 것과 전달되지 않는 것

전달됨 (공개 취약점 데이터)

  • CVE ID · CVSS 점수와 벡터 · CWE
  • EPSS 점수와 백분위
  • CISA KEV 등재 여부와 등재일
  • 공개 exploit 존재 여부 · 성숙도 · 출처
  • advisory가 지목한 패키지명 · 생태계
  • advisory 상의 영향 버전범위 · Fixed Version
  • OS 계열 (rhel · debian 등)

전달되지 않음 구조적으로 불가

  • 자산명 · 호스트명 · IP · 내부 URL
  • 파일 경로 · 사용자명 · 사내 레지스트리 · 이미지 태그
  • 부서 · 담당자 · 자산 ID
  • 설치된 실제 버전
  • 취약 여부 · 업데이트 가능 여부 판정
  • 대응 검토 우선순위
  • SBOM 전체 목록 · 발견 자산 수

AI는 우선순위를 산출하지도, 입력으로 받지도 않는다. 서술을 담는 자료구조에 우선순위를 담을 자리가 타입 수준에서 존재하지 않으므로, 모델 응답이 등급을 바꾸는 것은 구조적으로 불가능하다. 패치 명령도 AI가 만들지 않는다 — 운영 서버에 입력될 명령어를 생성 모델에 맡기면 환각의 대가가 너무 크다.

판단할 수 없으면 '미확인'

비표준 버전 문자열을 만났을 때 "취약하지 않음"이라고 답하면 그 취약점은 조용히 사라진다. 비교 불가는 unknown으로 남기고 사유를 리포트에 적는다. 같은 원칙이 위협정보에도 적용된다:

  • EPSS를 못 받아왔으면 0.0으로 채우지 않는다 → unknown_epss
  • KEV 조회에 실패했으면 "등재 안 됨"으로 처리하지 않는다 → unknown_kev
  • exploit 저장소를 못 읽었으면 "없음"이 아니다 → unknown_exploit
  • 스냅샷이 오래되었으면 → stale_snapshot

대응 검토 우선순위 정책

rules/priority.json은 기본 정책이다. config/priority.local.json으로 조직 기준에 맞게 임계값을 덮어쓸 수 있고(형상관리 제외), 리포트에는 적용된 정책의 버전과 sha256이 기록되어 "어떤 기준으로 판정했는지"를 사후에 추적할 수 있다.

명칭은 "위험도"가 아니라 "대응 검토 우선순위"다. 공개 데이터에 룰을 적용한 결과일 뿐이며, 자산의 노출 경로·보상 통제·업무 영향을 함께 고려한 최종 판단은 보안담당자의 몫이다.

데모는 어떻게 동작하는가

GitHub Pages에는 서버가 없습니다. 그래서 프론트엔드를 스캔 제공자로부터 분리했습니다. 실 운영에서는 로컬 FastAPI가 진짜 Grype 서브프로세스를 돌리고, 데모에서는 브라우저 매칭 엔진이 돕니다. 나머지 코드는 어느 쪽인지 알지 못합니다.

인덱스 생성CI에서 진짜 Syft + 진짜 Grype로 구버전 고정 이미지를 스캔해 취약점·영향 버전범위를 뽑고, EPSS·KEV·Exploit 스냅샷을 결합합니다 (주 1회)
브라우저 매칭Grype가 하는 것과 같은 판정 — 설치 버전이 advisory의 영향 버전범위에 드는지 생태계 규칙(rpm EVR · semver · PEP 440 · deb)으로 평가합니다
이후 전 과정FixAnalysis · 룰엔진 · 보고서 조립 · 이그레스 가드가 전부 브라우저에서 돕니다. 업로드한 SBOM은 어디로도 전송되지 않습니다

그래서 샘플 SBOM에서 패키지를 지우거나 버전을 바꾸면 결과가 실제로 달라집니다. 취약한 패키지를 지우면 그 항목이 사라지고, 버전을 Fixed Version으로 올리면 영향 범위를 벗어나 탐지되지 않습니다.

인덱스에 없는 패키지는 "인덱스 미수록"으로 정직하게 표기합니다. 조용히 "취약점 없음"으로 처리하지 않습니다. 인덱스가 아는 패키지(covered)와 취약점이 있는 패키지(vulns)를 구분해 담기 때문에 가능합니다.

데모의 AI 서술 (선택)

데모 보고서는 AI 없이 이미 완결되어 있습니다. 원하는 방문자는 자기 Google AI Studio 키로 ②기술적 위험성과 ④대응 필요성 분석의 서술을 생성해 볼 수 있습니다.

  • 우리 키는 배포물에 없습니다. 방문자의 키는 그 탭의 sessionStorage에만 저장되고(탭을 닫으면 사라집니다) 저희 쪽 어디로도 전송되지 않습니다.
  • 호출은 브라우저에서 Google로 직접 갑니다. 서버가 없는 경로이므로 브라우저 이그레스 가드가 유일한 방어이며, 통과하지 못하면 네트워크 호출이 일어나지 않습니다.
  • 전송 대상은 「AI에게 전송될 내용 보기」가 보여 주는 것과 정확히 같습니다.
  • 표현 정책(rules/tone-policy.json)에 걸린 서술은 반영하지 않고 룰 기반 문장을 그대로 씁니다.
  • 대응 검토 우선순위는 로컬 룰 엔진의 산출물이며 AI 응답이 바꾸지 못합니다 — 서술을 담는 자료구조에 등급을 담을 자리가 타입 수준에서 없습니다.

폐쇄망 운영

SBOMSight 자체는 인터넷이 되는 PC에서 돈다. "폐쇄망"은 패치 대상 서버 이야기다.

  1. 폐쇄망 안에서 syft로 SBOM을 생성해 JSON으로 반출한다.
  2. 반출한 SBOM을 SBOMSight가 도는 PC에 올린다.
  3. 탐지·보강·판정을 거쳐 보고서를 받는다. 보고서의 권고사항에는 폐쇄망 패치 절차가 담긴다.
  4. 인터넷 가능 구간에서 RPM과 의존성을 확보(dnf download --resolve --alldeps)해 반입하고, rpm -K로 서명을 검증한 뒤 dnf localinstall 또는 createrepo_c로 로컬 저장소를 구성해 적용한다.
  5. rpm -q와 SBOM 재생성·재스캔으로 검증한다.

SBOMSight PC 자체를 오프라인으로 운영할 수도 있습니다. SBOMSIGHT_OFFLINE=1로 두면 Grype DB 자동 갱신을 시도하지 않고 반입한 스냅샷으로만 동작합니다. 위협정보(EPSS · KEV · Exploit)도 캐시된 스냅샷을 쓰며, 확보하지 못한 소스는 unknown으로 남아 보고서에 그렇게 표기됩니다 — 0으로 채우거나 "없음"으로 처리하지 않습니다.

DB·스냅샷 반입 절차와 환경변수는 docs/offline-operations.md에 정리되어 있습니다.

SBOMSight · 대응 검토 우선순위는 정책 룰의 산출물이며, 내부 위험도와 최종 패치 여부는 보안담당자가 판단합니다.
